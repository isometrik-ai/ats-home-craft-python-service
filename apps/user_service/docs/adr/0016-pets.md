## Context

Residents manage a **household profile** in the MyNest mobile app: Family, Daily Help, Vehicles,
Tenant, and **Pets**. Product screens show:

1. **Household hub** — “My Pets” section with **+ Add** and a count tile on My Profile.
1. **Add pet wizard** — select pet type → breed → name → vaccination status → profile photo.
1. **My Pets list** — cards with name, vaccination label, and breed.
1. **Pet profile** — banner, photo, vaccination badge, type/breed, unit address, household owners,
   edit, and remove (with mandatory reason).
1. **Edit form** — name, type, breed, date of birth/adoption, gender, vaccination, photo.

### Product decisions (from Figma)

| #   | Decision                                                                                                                                                                                               |
| --- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 1   | Pets are **unit-scoped household records**, like vehicles — not contacts and not auth users.                                                                                                           |
| 2   | Any resident with an **active `contact_units`** link to the unit may add/edit/remove pets for that unit (Owner, Tenant, Family with unit access — same gate as vehicles).                              |
| 3   | **Pet types and breeds** come from a **static JSON catalog** (`app/data/pet_catalog.json`), served read-only via API — same pattern as `vehicle_catalog.json` / `VehicleCatalogService`.               |
| 4   | **Pet type and breed must be catalog selections only** — `pet_type` and `breed` store catalog **display names** validated against `pet_catalog.json`. No custom free-text values.                      |
| 5   | **Vaccination status** is self-declared at create/edit: `completely`, `partially`, `not_taken`. UI copy states admin may verify later (Phase 2).                                                       |
| 6   | **Remove profile** requires a **non-empty reason**; row is soft-deleted (`status = removed`) with audit event — not a hard delete.                                                                     |
| 7   | **No onboarding wizard step** for pets (unlike legacy `vehicles` / `household` steps). Pets are optional post-onboarding household data.                                                               |
| 8   | **Household summary** card count includes active pets on the unit (`GET /household/summary` extended with `pets_count`).                                                                               |
| 9   | **`created_by_contact_id`** records the resident who created the profile — set server-side from the authenticated caller on `POST /pets`; not accepted in the request body and immutable after create. |

### Constraints (carried from existing flows)

- Multi-tenancy via **`organization_id`** on every new table and query.
- **Resident actor** = `contacts` via `extract_onboarding_contact_context()`; must hold active
  `contact_units` for the target `unit_id`.
- Photos store **storage paths only** in `photo_paths text[]` — no blobs in Postgres (same pattern as `vehicles.photo_paths`).
- Mutations audited via existing `@audit_api_call` on pet routes; removal reason stored on `pets`.
- Catalog JSON is **version-controlled in the repo**; updating breeds does not require a migration.

## Decision

### 1. One new table — `pets`

Pets are first-class rows on a dedicated table (not JSONB on `contact_units`). Create/update/remove
actions are audited via the standard API audit decorator; soft-remove stores `removal_reason` and
`removed_by_contact_id` on the pet row.

| Table      | Purpose                                                                                     |
| ---------- | ------------------------------------------------------------------------------------------- |
| **`pets`** | Pet profile: identity, pet_type, breed (catalog names), vaccination, photo_paths, unit link |

> **Why not reuse `vehicles` or `daily_help_profiles`:** pets have different fields (breed, vaccination,
> gender, DOB) and no gate pass / parking / admin approval queue in Phase 1. A dedicated domain keeps
> validation and household summary queries simple.

### 2. Static JSON catalog — not Postgres lookup tables

Pet types and breeds live in **`apps/user_service/app/data/pet_catalog.json`**.

- **`PetCatalogService`** (mirror of `VehicleCatalogService`) loads and caches the file.
- **`GET /v1/pets/catalog`** returns types; optional `pet_type_id` filters breeds; optional `search`
  filters names case-insensitively.
- Create/update payloads store **`pet_type`** and **`breed`** as catalog display names (e.g. `"Dog"`, `"Golden Retriever"`).
- Catalog JSON retains `id` fields for picker UX and `GET /pets/catalog` filtering; ids are **not** persisted on `pets`.

**Catalog shape:**

```json
{
  "pet_types": [
    {
      "id": "dog",
      "name": "Dog",
      "icon": "dog",
      "breeds": [
        { "id": "labrador_retriever", "name": "Labrador Retriever" },
        { "id": "golden_retriever", "name": "Golden Retriever" }
      ]
    }
  ]
}
```

**Stored vs catalog:**

| DB column  | Example value      | Catalog match                        |
| ---------- | ------------------ | ------------------------------------ |
| `pet_type` | `Dog`              | `pet_types[].name`                   |
| `breed`    | `Golden Retriever` | `pet_types[].breeds[].name` for type |

No separate label columns — stored values are what the UI displays.

### 3. Catalog validation rules

Enforced in `PetsService` (and Pydantic models):

| Field                | Rule                                                                   |
| -------------------- | ---------------------------------------------------------------------- |
| `pet_type`           | Required; must match a type `name` in catalog (case-insensitive)       |
| `breed`              | Required; must match a breed `name` under that type (case-insensitive) |
| `name`               | Required; 1–100 chars                                                  |
| `gender`             | Optional enum: `male`, `female`                                        |
| `date_of_birth`      | Optional date; must not be in the future                               |
| `vaccination_status` | Required enum: `completely`, `partially`, `not_taken`                  |
| `photo_paths`        | Optional `list[str]` of storage paths; default `[]`; max 10 (proposed) |

Invalid or unknown names return `pets.errors.invalid_pet_type` / `pets.errors.invalid_breed`.

### 4. Resident API — `/v1/pets`

| Method | Path                       | Purpose                                        |
| ------ | -------------------------- | ---------------------------------------------- |
| GET    | `/v1/pets/catalog`         | Pet types + breeds (static JSON)               |
| GET    | `/v1/pets`                 | List pets for caller’s units (`?unit_id=`)     |
| GET    | `/v1/pets/{pet_id}`        | Detail (owners, unit label, vaccination badge) |
| POST   | `/v1/pets`                 | Create pet (`unit_id` required)                |
| PATCH  | `/v1/pets/{pet_id}`        | Update profile fields / photo_paths            |
| POST   | `/v1/pets/{pet_id}/remove` | Soft-remove with `{ "reason": "..." }`         |

Auth: `extract_onboarding_contact_context()`. Every write validates active `contact_units` for
`(contact_id, unit_id)`.

On **create**, the service sets `created_by_contact_id` to the caller’s `contact_id`. List and detail
responses include a nested **`created_by`** object (display name, photo) for the resident who added
the pet — used on the pet profile “Owner details” section.

**`created_by` response shape (list + detail):**

```json
{
  "created_by_contact_id": "contact-uuid",
  "created_by": {
    "contact_id": "contact-uuid",
    "display_name": "Ajay Thakur",
    "profile_photo_url": "org/contacts/ajay.jpg",
    "relationship": "self"
  }
}
```

**Household summary extension:**

```json
GET /v1/contact-onboarding/household/summary?unit_id=
{
  "data": {
    "family_count": 2,
    "daily_help_count": 2,
    "vehicles_count": 2,
    "tenant_count": 1,
    "pets_count": 2
  }
}
```

`pets_count` = rows where `status = active` and `deleted_at IS NULL` for the unit.

### 5. Admin vaccination verification (Phase 2 — optional)

Phase 1 stores resident-declared `vaccination_status` only. Phase 2 may add:

- `vaccination_verified_at`, `vaccination_verified_by_user_id`, `vaccination_verification_note`
- Admin routes under `/v1/projects/{project_id}/pets` with list + verify/reject
- Push notification to pet owner on verification outcome

Not in scope for initial migration; columns can be added nullable in Phase 2 without breaking Phase 1 clients.

### 6. Status lifecycle

#### `pet_status` enum

| Status    | Meaning                                     |
| --------- | ------------------------------------------- |
| `active`  | Visible in household lists and profile      |
| `removed` | Soft-deleted; hidden from lists; audit kept |

```text
POST /pets ──► active

active ──POST /pets/{id}/remove { reason }──► removed
         (sets deleted_at, removal_reason, removed_by_contact_id)
```

No `pending` / admin-approve gate in Phase 1 (unlike vehicles).

### 7. RBAC split

| Actor    | Routes                           | Auth                                         |
| -------- | -------------------------------- | -------------------------------------------- |
| Resident | `/v1/pets/*`                     | Onboarding contact context + unit membership |
| Admin    | `/v1/projects/{project_id}/pets` | Phase 2 — staff RBAC + project access        |

## Schema (proposed)

### Enums

```sql
CREATE TYPE public.pet_vaccination_status AS ENUM (
  'completely',
  'partially',
  'not_taken'
);

CREATE TYPE public.pet_gender AS ENUM (
  'male',
  'female'
);

CREATE TYPE public.pet_status AS ENUM (
  'active',
  'removed'
);
```

### `pets`

| Column                      | Type                            | Notes                                                                                   |
| --------------------------- | ------------------------------- | --------------------------------------------------------------------------------------- |
| `id`                        | uuid PK                         |                                                                                         |
| `organization_id`           | uuid FK → organizations         |                                                                                         |
| `project_id`                | uuid FK → projects              | Denormalized from unit for project-scoped admin queries                                 |
| `unit_id`                   | uuid FK → units                 | Household unit                                                                          |
| `created_by_contact_id`     | uuid FK → contacts              | Resident who created the profile; set on insert, never updated                          |
| `name`                      | text NOT NULL                   | Display name                                                                            |
| `pet_type`                  | text NOT NULL                   | Catalog type display name (e.g. `Dog`)                                                  |
| `breed`                     | text NOT NULL                   | Catalog breed display name (e.g. `Golden Retriever`)                                    |
| `gender`                    | pet_gender                      | Optional                                                                                |
| `date_of_birth`             | date                            | Optional; DOB or adoption date                                                          |
| `vaccination_status`        | pet_vaccination_status NOT NULL | Resident-declared                                                                       |
| `photo_paths`               | text[] NOT NULL                 | Profile photo storage paths; default `'{}'`; order preserved — index 0 = primary avatar |
| `banner_path`               | text                            | Optional header banner (defaults to themed placeholder in UI)                           |
| `status`                    | pet_status NOT NULL             | Default `active`                                                                        |
| `removal_reason`            | text                            | Set on remove; required non-empty                                                       |
| `removed_by_contact_id`     | uuid FK → contacts              | Set on remove                                                                           |
| `deleted_at`                | timestamptz                     | Set on remove                                                                           |
| `sort_order`                | integer NOT NULL                | Default 0; list ordering within unit                                                    |
| `created_at` / `updated_at` | timestamptz                     |                                                                                         |

**Indexes / constraints:**

- `(organization_id, unit_id, status)` — household list + summary count
- `(organization_id, created_by_contact_id, status)` — pets created by a resident across units
- `(organization_id, project_id, status)` — admin list (Phase 2)
- `(organization_id, unit_id, lower(name))` — search

## Consequences

### Positive

- **Familiar patterns** — mirrors vehicles (unit scope, contact creator) + vehicle catalog (static JSON pickers).
- **Simple schema** — `pet_type` and `breed` stored as display names; no separate key/label columns.
- **Household integration** — one extra count on existing summary endpoint; no new onboarding step.
- **Audit trail** — removal reason on `pets` plus API audit logs on create/update/remove.
- **Phase 2 ready** — admin vaccination verification can extend the same `pets` table.

### Negative / trade-offs

- **Catalog drift** — new breeds require a JSON deploy, not admin UI (acceptable for v1; admin CRUD is a follow-up).
- **No cross-unit pet** — one pet row per unit; same physical pet in two units needs two rows (matches vehicles).
- **Self-declared vaccination** — gate/security cannot trust status until Phase 2 verification.
- **Catalog renames** — if a catalog `name` changes, existing rows keep the old string until edited.
- **No free-text type/breed** — unlisted values require a catalog JSON update and redeploy.

### Follow-ups

1. Signed upload URLs for pet photos (reuse existing media upload flow).
1. Admin vaccination verification + project-scoped pet registry.
1. Optional project-level pet policy limits (max pets per unit).
1. i18n message keys under `pets.*` in `app/locales/en.json` (done in Phase 1).

## Alternatives considered

| Alternative                                | Why rejected                                                             |
| ------------------------------------------ | ------------------------------------------------------------------------ |
| Postgres `pet_types` / `pet_breeds` tables | Overkill for v1; product wants curated list in repo like vehicle catalog |
| Store only free-text type/breed            | Loses structured filters, icons, and search in wizard                    |
| Reuse `vehicles` table                     | Wrong domain fields; confuses admin vehicle review                       |
| Hard delete on remove                      | Product requires reason capture and audit                                |
| Global enum for pet types                  | Every new type needs migration; conflicts with JSON catalog approach     |
